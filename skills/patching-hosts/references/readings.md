# Readings: what to measure before proposing a run

What `probe.sh` reads, and the checklist for what it leaves to you. Each reading is paired with **the mistake it prevents**: in #313's step 0 round, every one was misread, or found by hand, on at least one host.

**The probe changes no host state but Ubuntu Pro's and the dry run's** (#501, #696): run as root, `pro security-status` appends to `/var/log/ubuntu-advantage.log`, takes `/var/lib/ubuntu-advantage/lock`, and rebuilds apt's binary cache and its own under `/var/lib/ubuntu-advantage/apt-esm`. Beyond that it leaves what any read leaves: sudo's record of each escalation, a server's of a connection. It runs the knob's `health` lines, so each must be safe and cheap at any time; a check with side effects is a `recovery` line, run only under `--post-boot` (#423). Otherwise it reads: the unit scan reads unit files and drop-ins (#508), and under `--refresh-into` without `--no-language`, `uv --version` and `uv audit` run as `nobody` against a root-owned `uv.lock` (#456). It writes only to its own scratch directory (`mktemp -d`, removed on exit) and the ones you name. No apt call of its own, the dry run's included, writes apt's binary cache or logs: as root, a simulation rewrote the planner log, `eipp.log.xz`, and the dry run `history.log` (CR 2773).

- `apt-get update` writes the package lists. The probe refreshes only with `--refresh-into DIR`, into `DIR/lists`, with the host's `APT::Update` hooks cleared (#696). Run as root on a 24.04 image, they started `apt-news` and `esm-cache`, and touched `update-success-stamp`, which reads as the host's last update. The host's own lists stay as they were, so a by-hand `apt-cache policy` reads old candidates: read beside the probe with `-o Dir::State::Lists=DIR/lists` (2026-11-16 watcher, #669).
- **The security count's dry run** (`unattended-upgrade --dry-run -d`) runs as root and downloads the whole set: about 290 MB and 9 minutes on address-validator. It runs only with `--dry-run-into DIR`, apt's cache pointed at `DIR/archives` through an `APT_CONFIG` file, since `unattended-upgrade` takes no `-o`. **It sizes that download first** (#499): `apt-get --print-uris` over the pending set, or the one origin's packages, an upper bound. Where that wouldn't fit on `DIR`'s filesystem with 128 MiB left, or can't be read, it doesn't start, and a `dry-run` finding says so; nor without `--refresh-into`, on a security list fetched more than 24 hours ago or one it can't date (#629). It leaves `DIR/summary`, whose wall time `apply.sh --dry-run DIR` takes as the floor of each step's expected duration, adding the health checks' time; `apply.sh` refuses one more than 24 hours old. Its own logs go to `DIR/unattended-upgrades`. It still writes `/var/lib/apt/periodic/unattended-upgrades-stamp`, which apt's daily job doesn't read, and `/run/unattended-upgrades.{lock,progress}`, and runs the host's `DPkg::` hooks, which python-apt re-reads after any `APT_CONFIG`: on 24.04, update-notifier's touches `dpkg-run-stamp` and the motd's count; needrestart's, with nothing unpacked, runs nothing. Without it, the security count is a lower bound; with it, exact only while the host's unattended-upgrades origins are `-security` alone, which `security_only` says.

A read can change the host without writing a file: a socket-activated daemon starts on its first client. exeuntu enables `docker.socket` and disables `docker.service`, so the probe asks Docker only while `docker.service` already runs. Asking an idle Docker would start it, and restart the idle clock its dormant verdict reads.

The probe reads the root-only readings through `sudo -n`, so it never prompts, and `probe.privilege` reads `sudo` when it did: an owner whose every sudo step is a gate approves the probe as one, or passes `--no-sudo`, which leaves those readings in `not_read` (#490). With `--root DIR` it reads an image tree's files, and asks a running system only when `DIR/run/systemd/system` exists, the test systemd itself uses.

**Report an absent setting as `unknown`, never as its default.** A reading the probe couldn't take is `unknown`, not clean. That includes a read that needed root and failed: `/proc/<pid>/maps` of another user's process, needrestart's check, the Postgres catalogs. Under a read-only sandbox (`ProtectSystem=strict`), pro can't write its log, and `not_read` says so, apart from a pro that failed otherwise: the run has no ESM counts (#501).

## The environment

| Reading | How | Mistake it prevents |
|---|---|---|
| Which profile, and which image generation | markers, not a digest ([environments/exe-dev-exeuntu.md](environments/exe-dev-exeuntu.md)) | assuming the newer image's `exe-setup`, journal and `/tmp` rule on an older host, or its `exe-init` layout from its generation |
| The exe.dev image's identity | `/exe.dev/etc/image.conf`'s OCI labels `org.opencontainers.image.created`, `.revision` and `.version` (`main` or `nightly`), in `environment.image_conf` (#388) | dating an image by markers alone, when the guest can read its build time, commit and channel |
| `exe-init`'s layout | the `exe-init` processes resident and their roles: root's, whose `/proc/<pid>/exe`, read as root, is `/exe.dev/bin/exe-init`, never an operator's `exe-init --version`. `guestd`, `op-ssh+memd` or `init-only`, in `environment.exe_init` (#388) | inferring the layout from the generation: the April 2026 image dates `may-2026` and is init-only |
| Boot time | `/proc/stat` btime | `who -b` was wrong on three hosts |
| **Where the journal actually lives** | files under `/var/log/journal`; `systemctl is-enabled systemd-journal-flush`; the days the oldest entry reaches back. `Storage=` is read as journald reads it (#608): its main file from `/etc` on systemd 255 and older, and from 256 the first of `/etc`, `/run`, `/usr/local/lib` and `/usr/lib`, by the dpkg database's version (unread, as 256 does, in `not_read` when that's not `/etc`'s); then the drop-ins by name (#515). Only `[Journal]` counts, a line is trimmed, and a value journald can't parse, an empty one included, is ignored, keeping the one before | `Storage=persistent` with the flush masked: address-validator's 51 days were lost at the reboot |
| PID 1's log target | live, and argv's `--log-target`. A daemon-reload applies `SYSTEMD_LOG_TARGET`, the kernel's `systemd.log_target=` or `system.conf`'s `LogTarget=`, else keeps the live one; a re-exec applies argv's first. An unseen `set-log-target` survives both (`pid1_logs_to_journal`) | reading the new boot's target as the one the previous shutdown ran on (#684) |
| **The session's chain to PID 1** | the adj of every process from `$$` up, read directly. The session's own part ends below the platform's agent, `exe-init` or `sshd`, whose -1000 is reported apart: stock OpenSSH's listener runs at -1000 and starts each session at 0, as exe.dev's `sshd` does on the older layouts (#353, #346) | a host test that skips when the parent isn't `exe-init`/`sshd`, reading green (CannObserv/watcher#333) |
| **What consumes a setup script** | `exe-setup.service`'s `LoadState`, and its `ConditionResult` and `Result` for each retained boot; `/exe.dev/setup`'s mode and owner, and whether the unit is disabled; secret patterns by name and line, **never the value** | taking an absent file as cleanup, when the platform delivers it again every boot; and reporting a file contained in place, root's alone with the unit disabled, as a leftover |
| **Anything staged under `/tmp`** | `ls -la /tmp`; `/usr/lib/tmpfiles.d/tmp.conf` and `/etc/tmpfiles.d/` | losing a staged binary to `D /tmp` at the reboot (CannObserv/wslcb-licensing-tracker#182) |

## What updates this host

| Reading | How | Mistake it prevents |
|---|---|---|
| The apt timers and service | `systemctl is-enabled`, or the mask symlinks on disk (works offline) | trusting `20auto-upgrades`' `1`/`1` |
| **The effective `Periodic::Enable`, and which file sets it** | `apt-config shell E APT::Periodic::Enable`; grep `/etc/apt/apt.conf.d/` | missing `docker-disable-periodic-update`'s `0`, which makes unmasked timers no-ops |
| Every apt source, and each origin | `/etc/apt/sources.list.d/`, `apt-cache policy` | treating a third-party origin as Ubuntu's |
| **Each followed origin's scope** | `apt-cache policy`: the priority on its release lines, which a `Package: *` pin for its site moves, and its `Pinned packages:`; then `apt-cache policy` over every installed package, for each candidate's site | a third-party package taking an Ubuntu name's place at 500, or the lane taking whatever the origin serves that's installed, not what it was added for ([policy.md](policy.md#two-lanes)) |
| The needrestart config in force | `sudo needrestart -m u -b -r l`'s `Disabling Ubuntu mode` line | a drop-in that doesn't load, leaving the hook in automatic mode |
| Tailscale's running version | `tailscale version --daemon --json`'s `daemonLong`, beside `tailscale version`'s client version | an upgrade whose restart didn't happen: the CLI reports the fix while tailscaled still runs the old binary, and plain `tailscale version` never says so |
| Tailscale's own auto-update | `tailscale debug prefs`: `AutoUpdate.Apply` is true, false, or null when nothing ever set it on the node. The tailnet's setting configures a device only as it joins, and never changes an existing one | the host's tailnet path, and anything that reaches it over the tailnet, dropped by an upgrade nobody scheduled |
| **When it was last run** | the newest of the `/var/backups/patching-hosts-<UTC>` run directories and the marker `/var/backups/patching-hosts-last-reading` that a run with no bulk record writes ([run.md](run.md#a-run-with-nothing-pending)). A directory is dated by the bulk's start in its `steps`, which `apply.sh` writes as the bulk ends; else by the fire time in `reboot-chain.unit`; else by its name, when it was made, which the period floor absorbs. So the count runs from the last attempt, not the last success: a failed or abandoned one, such as a recovery point whose bulk never ran, resets it, and its own record shows the failure. A stamp more than an hour past the probe's clock is in `not_read`, never the last run; within the hour, it's now. Never the records: no `gh`, no network. Under `scheduled`, `updates.cadence` counts the periods missed, weeks or months, and the weekday and `#N` windows closed since (`monthly`'s rule: [knob.md](knob.md)); one or more is `cadence:overdue` (#592). When the newest two run directories' bulks both started outside every weekday and `#N` window, that's `cadence:off-window`: one dated otherwise stops it, and the marker is passed over ([knob.md](knob.md), #708). No run on disk, a retention sweep's included, is `cadence:no-run`, never "not overdue"; a marker that doesn't parse is in `not_read`. `automatic` has no window to miss, nor has a host whose only windows are dated: `unchecked_why` says so | a missed window nobody saw: wslcb's four Tuesday windows passed while 51 security packages piled up (2026-10-13 to 11-03), and co-processor's weekly window passed unattended (2026-11-03) |
| **Everything outside apt, with its owner** | `/usr/local/bin`, `~/.local/bin`, container images and their age, pinned tools | a component nobody patches because nobody owns it |

## The pending set, by class

| Reading | How | Mistake it prevents |
|---|---|---|
| List age | when the security `InRelease` was last fetched, its ctime; its mtime is the archive's `Last-Modified`, which a quiet day for the archive ages (#493). A ctime is also a tree's unpacking, so it counts only when more than an hour newer than `/usr/lib/os-release`'s, which no fetch writes: a layered unpack spans seconds, and the lists sit in a later layer (CR 1300); otherwise the age is the mtime's, and `lists.source` says so (CR 1295) | a count against stale lists, which measures provisioning, not the image |
| A refresh | `--refresh-into DIR` runs `apt-get update --error-on=any` into `DIR/lists`. **A source that fails to fetch fails the whole refresh** (exit 100): `pending.lists.refreshed` is false, the `lists:refresh` finding names the exit, and every count is against the host's own lists, which List age then dates (#542). The bulk's own `apt-get update` takes the same flag, so a failed source stops it before anything is held. The flag needs apt 2.1.16 (noble ships 2.8): an older apt refuses it, so every refresh and bulk reads as failed. **A source that's down for good**, such as a dead PPA, stops every lane, the one-origin lane's urgent window included, until it fetches again or is removed: the owner's change to the host's apt sources, never the skill's | `apt-get update` exits 0 when one source fails, and leaves that source's lists as they were: a lane counted, and the bulk upgraded, against a source's old lists, or none, and the finding never fired |
| **Security, counted right** | `unattended-upgrade --dry-run -d`'s `Packages that will be upgraded` line | `apt list \| grep -security` undercounts (usa-wa: 178 against 185), and `grep \| head` on the one-per-line header truncates |
| `-updates` and third-party | `apt list --upgradable` against each origin. Canonical's own origin, such as the Ubuntu Cloud Archive's, is first party, as the knob and the exposure read it: it counts in `ubuntu_other` whatever its archive, never in `third_party` (#609). A third-party package is keyed on its repo's `o=`, as the knob names it, not the Label `apt-get -s` prints: the ondrej/php PPA's is `PPA for PHP (deprecated)`, and packages.sury.org has none, so it printed the suite (#695). One `apt-cache policy` can't map, or that two origins print alike, keeps apt's text | treating the security count as "everything" |
| **Ubuntu Pro / ESM** | `pro security-status` | "0 security pending" read as covering `universe` (wslcb: 29 esm-apps pending) |
| **Language dependencies** | each unit's `WorkingDirectory=` holding a lockfile; `uv audit --frozen` on a copy of its `pyproject.toml` and `uv.lock`, as the lockfile's owner, never as root and never in the tree (`pending.language`). A root-owned lock, such as a deploy's release tree, is audited as `nobody`, with a root-owned `/usr/local/bin/uv` or `/usr/bin/uv`, never a user-writable one (#456). Switching user needs root: under `--no-sudo`, or where `sudo -n` needs a password, the tree isn't audited, and its `why` and `not_read` say so (#635). It asks OSV, so only under `--refresh-into`, never in `apply.sh`'s probe after a step, and not with `--no-language`, for a report that drops `pending.language`: then `null`, and `not_read` says it wasn't asked (#702) | a host reported clean while its service runs a vulnerable TLS or crypto library from its own venv (notifier, #366). Any other lockfile is listed as not audited, never as clean, and a tree uv couldn't audit says why. A knob `service` whose `WorkingDirectory=` holds no lockfile has `lockfile: null` (#508); a unit file or drop-in the probe couldn't read is in `not_read`, since the tree it sets may be missing. A uv with no `audit` names its version and 0.10.8, the first with one, for the tree's `owner` to upgrade; the probe never fetches uv (#422). Either way the class reads `complete: false`. Per package, `ids` lists its advisories, and `fixed_in`, in order, the versions that fix each: `[]` where uv says none does, `null` where it printed neither line (#594) |
| **Phased updates** | the simulation with `APT::Get::Always-Include-Phased-Updates`, and `(phased N%)` in `apt-cache policy`. Where one is phased, the simulation without it too: `pending.phasing.deferred` are those apt would defer on this machine, `in_phase` the rest, and `dry_run.phased_deferred` the deferred the lane takes, which the knob's `phasing respect` leaves ([knob.md](knob.md), #686) | a count that leaves out what the lane takes: apt defers a phased update outside its phase, and unattended-upgrade takes it anyway (replicator: 34 counted, 35 taken; #354). A lane that forces what apt defers: address-validator's took all 22 phased `-updates`, where apt deferred 13 |
| The dry run against the classes | what the dry run selects that no class list names, and each package it passes over at a conffile prompt, with the state of its conffiles on disk. Its class still counts it, and `by_class.passed_over` marks it there (#361) | a package reaching the host that the proposal never showed, or a count promising one the lane won't install |
| The dry run's cost | wall time, max RSS, download size; before it starts, its own download's upper bound (`download_bound_kib`) against `DIR`'s free space (`free_kib_dry_run_dir`, #499); what the run writes (`dry_run.space`: download, install growth and largest upgrade from apt's metadata) against the free space on apt's cache and `/`, each keeping 128 MiB, and the disk GC's headroom line where its config is there; free space on `/var/backups` beside it | a disk-full or memory-starved apply on a host that shares memory with sessions; a patch run that pages for headroom |
| The dry run's held versions | the candidate it counted of each package a hold group takes, in `DIR/summary`; compared outside the security lane, where the candidate can be a newer `-updates` version than the step takes | a held step that installs a release published since, which the owner approved without reading (#383) |
| Held-group candidates | which `hold` globs are in the set | a major version bump (docker.io 28→29) going in with the bulk |
| **Owner holds** | `apt-mark showhold` against the pending set and the knob's `held:` exceptions | a security fix deferred indefinitely by a hold nobody declared ([policy.md](policy.md#exceptions)) |

## Dormant components

For each engine the probe knows (Docker, Postgres, Redis, Valkey, nginx, Ollama, Qdrant to start with):
- the unit's state and whether it's enabled;
- its listeners;
- its workload: containers, databases with their sizes and their writes and sessions since the statistics were reset, Redis's keys, lookups, expirations, subscriptions and clients, enabled sites;
- whether the repo's units, docs or knob name it, as a word: a unit, a command, a path's own directory or file, a URL. Inside another name it doesn't count, so a unit running `check_redis_floor.sh` doesn't name Redis (#634). An `in-use` verdict quotes a `deploy/` line with its secrets masked, and a host unit by the word alone (CR 2158);
- its packages in the security set;
- how long it has been idle: since its unit's stop, or, for a unit that hasn't started since the boot, whichever reaches further back of the boot and evidence that outlives one (#633). That's its log directory's newest file (`/var/log/nginx`, `/var/log/redis`, `/var/log/postgresql`; all empty means never written; one it can't read keeps the boot's clock and is named in `not_read`, CR 2159, CR 2164), else the latest `Install:` of its packages in `/var/log/apt/history.log*`. Never dpkg's `.list` mtime, which every upgrade rewrites. The evidence names the clock;
- whether it shipped with the image or was installed later.

The verdict rules are in [policy.md](policy.md). **Name the evidence source for each verdict.** A journal that holds 10 days can't show 30 days of idleness.

## What the probe leaves to you

A reading it couldn't take is `null` in its output and named in `not_read`: no root, no running system, or no `pro`. These it never takes, so read them yourself:

- **callers and traffic**, from the service's own access or audit log;
- **what reads 200 while degraded**, from the code;
- **the suite's pass and skip counts**, for the health baseline;
- **whether a component came with the image**: that needs the image's build date, which the guest can't see;
- **the downtime** after a boot, from the stop line or the last request to the first good response.
