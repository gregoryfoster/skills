## Session 2026-09-29 — watcher

Host 8. CannObserv/watcher#331 closed 2026-09-29T00:08Z. It was the first host with local Postgres **and a working backup regime**, and it runs an in-process job queue. Patch only.

### Environment

exe.dev, on a 19-day-old image, as a 14-day-old VM. Provisioning had refreshed the lists, so they were only 13 days stale.

### Readings

- 50 security updates were applied, in 3 min 44 s.
- **Setup-script re-delivery was confirmed on a second host:** 4 of 4 boots. The owner revoked the spent key before the reboot, and the node rejoined on its stored identity.
- A hand start of the daily backup unit gave a fresh, verified, off-node dump.
- PostgreSQL 16 wasn't in the set, but its backends mapped `libc6` and `libxml2` from it. So needrestart listed the cluster, and the reboot was its restart.
- A graceful stop of the queue waits for running jobs. **systemd's stop timeout then SIGKILLs one,** leaving it `doing` forever; one sat there for 131 days on the old VM.

### What the profile lacked

- A long list of agent binaries outside apt, from the image, with no package owning any of them.
- `who -b` was right on this boot, after being wrong on three hosts. Read `/proc/stat` btime regardless.

### Decisions

- **Revoking a spent key is safe,** and it's the remedy for re-delivery.
- **Prefer the host's own backup regime** for the recovery point.
- **Read the check-in target from the host, not the brief:** check-ins had moved to a new status service that day.
- **The data store's question is whether any of its processes map a package in the set,** not whether its package is in it.
- **A queue needs a "nothing in flight" read inside the reboot chain itself:** here, a loop on `doing` until it's 0.
- **Read the session's OOM score directly,** up to PID 1. A host test had skipped and read as green.

### Surprises

The round's first completed prune, Docker's removal, left **the `docker` group with the session user still a member.** A prune has to cover groups and memberships.
