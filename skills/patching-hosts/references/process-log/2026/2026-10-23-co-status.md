### What the skill got wrong or lacked

1. **A pinned origin has no lane for a bulletin.** `policy.md` routes a bulletin to `apply.sh --lane origin:<origin>`, and that lane takes a *follow* origin only: "The lane never takes a pinned or held one: a pin moves only by hand." So moving the knob's pin to the fix still leaves no scripted way to install it.
   - The run went outside `apply.sh` entirely: no gate, no before-versions record, no run directory, no reprobe.
   - The recovery point's rule had to be judged by hand: no data-store package was in the set, so none was taken.
   - Proposed: `--lane origin:<origin>` accepts a `pin` origin and installs exactly the pinned version, refusing when the candidate differs. Moving the pin stays a hand edit to the knob, and the install gets the lane's gate and record.
2. **`inflight` reads only what's running now, not what starts inside the step.** The knob's `inflight` was 0. But a 60 s sweep that starts during tailscaled's ~2 s restart would fail its `/ready` check over the tailnet and send a `/fail` ping, a false page. The run was timed by hand to start 20–30 s into the minute, with the sweeps firing at :06–:11. `run.md` already gates on `apt-daily-upgrade.timer`'s span (calendar plus random delay). Proposed: the same span check for each timer whose unit the knob's `inflight` names, against a step's expected duration (for one origin's restart, seconds).
3. **needrestart's list after a step names services the step didn't touch.** After a `tailscale`-only step, `needrestart -m u -b -r l` listed both app services.
   - The cause was a day older: their `uv run` launcher maps a deleted `/usr/local/bin/uv`, replaced by `sudo uv self update` at 2026-10-22T18:16:48Z.
   - That ran in the sequence that ends `exeuntu update claude/codex/…` and installs `libnss3-tools`, consistent with exe.dev's `remediate-emudhra-compromise`. That's a claim: the journal shows the commands, not their caller.
   - Read alone, the list blames the step and asks for restarts the step didn't cause. Proposed: take needrestart's list before each step, and report the step's own additions apart from what was already there.
   - Profile fact: on exeuntu, a `uv run`-launched service shows up as an obsolete binary after any `uv self update` (measured 2026-10-23, co-status).

### Decisions

- **A hand run, pinned by version, under `NEEDRESTART_MODE=l`,** owner-approved in the host's session. The knob's pin moved to the fix in the same change.
- **No recovery point:** the set was `tailscale` alone, and no data-store package or library was mapped. That was judged under the Iron Law's intent, not by a gate, which is finding 1.
- **Neither app service was restarted for the stale `uv`.** The deploy that ships the host's certifi fix (below) restarts both.

### Surprises

- **The bulletin's fix doesn't finish the host's exposure.** Both deployed venvs carried a certifi release from July 2026, which still trusts `emSign ECC Root CA - G3`, and httpx reads certifi, not the system store. That needed a lock bump and a deploy: CannObserv/status#58, closed the same day. `probe.sh`'s "outside apt" and language-dependency classes are where a bulletin that names a root store would need it read.
