### What the skill got wrong or lacked

- **A reboot resets the `dormant` evidence.** Before the boot the probe called Docker and nginx dormant ("inactive for 45 days", which was the time since the last boot). After it, both findings were gone, since inactive time now dated from this boot. The run that reboots is the one that erases the 30 days the finding needs, so a weekly-reboot host might never show them. **Since fixed** (#633): a never-started unit's idle clock reads its log directory or apt's history, which a boot doesn't reset.
- **Each `uv run` timer service needs its own `not-restarter` exception.** That's 12 near-identical lines here (`restarters:unread:<svc>`), plus the `OnFailure=` notifier. A glob key such as `not-restarter:power-map-*.service` would let one reasoned line cover a family. archiver hit the same that night ([2026-11-14](2026-11-14-archiver.md)).
- **The maintenance lane is blocked on every exeuntu host that keeps `fwupd`,** by a conffile the image itself deletes. The profile records the trap and that unattended-upgrade exits 1 on it, and names fwupd as an `apt:` prune case, but doesn't say in so many words that it stops the maintenance lane's dry run. The finding (`dry-run:conffile:fwupd`) was clear about it.

### Decisions

- **Security lane only.** The maintenance lane's dry run exited 1, and the window was the owner's one-off. `-updates` goes to the first weekly window, after `fwupd` is settled.
- **The one-off window was set ahead**, at 21:00–23:55Z in a dated line merged before the probe, not from `date -u` at approval. It held because the owner approved the bulk, the held step and the reboot together, 15 minutes into it.
- **The `health` line checks the readiness route that reaches the DB**, not a liveness route. The egress IP that gates the DB can rotate across a reboot, and only the DB-reaching route sees that.
- **The host's knob guard tolerates `past-window` and `expired-exception`** and nothing else, so neither a dated one-off line nor a prune's soak ending reds the suite. It's the same tolerance as wslcb's guard ([2026-11-07](2026-11-07-wslcb-licensing-tracker.md)). A soak's end is now its own kind, `soak-ended` (#636), which a guard like this one must allow too.
- **After the run, the owner pruned all three dormant components**: Docker, nginx and fwupd, each with the disable stage and a 30-day soak. fwupd is also held (`held:fwupd`) until its purge, so its conffile prompt can't stop the maintenance lane.
- **Tailscale's auto-update went off on the node** (`tailscale set --auto-update=false`); the tailnet default is the owner's, in the admin console.
- **The three third-party origins are followed.** Declaring them raised `unscoped:<site>` and `unpinned:<package>` at once: each origin sits at priority 500 with no `Package: *` pin. The pins are host apt config, the owner's to add before the first maintenance-lane run; they went in the same evening.

- **The run was short:** 12.5 minutes from the bulk's start (21:04Z) to `/ready` 200 after the boot (21:16:45Z), and 32 minutes from the first probe. With no data store and no held step taken, it needed only three approvals.
