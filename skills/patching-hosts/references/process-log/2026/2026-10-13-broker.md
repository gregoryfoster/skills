## Session 2026-10-13 — broker

The fifth run under the scripts, and this host's first (#313 step 8b; CannObserv/broker#67). It's the cohort's **Redis bus**: five participants on the tailnet publish to it and consume from it. It's the first host with a Redis data store, the first whose own backup stood in for the dump, and the first with a `redis` held step. The run also caught up the host's maintenance lane.

### Environment

- exe.dev, `exe-dev-exeuntu` (Ubuntu 24.04).
- Redis 7 from Ubuntu, `appendonly yes` (multi-part AOF) with save points set. It binds the tailnet address and waits for it at start. It logs to a file, not journald.
- Redis runs an `aclfile`, and `default` is off: `-@all`, with a password nobody holds. `requirepass` in `redis.conf` is a random value belonging to no user. The operator's identity is an ACL user whose password is a `systemd-creds` credential, decrypted by root on demand.
- The host's own backup ships the RDB file off the node every hour (`Persistent=true`, 5 minutes of jitter). The journal is persistent.
- Posture `scheduled`, window Mon 23:00–05:00 UTC.

### What the skill got wrong or lacked

- **The Redis scripts log in as `default` with `requirepass`** (#379). On an ACL'd Redis whose `default` is off, the chain's ownership gate got `WRONGPASS`, then `NOAUTH`, and refused as if it had reached no Redis. So `reboot-chain.sh` couldn't run. Each attempt also wrote an `ACL LOG` entry the host had to attribute.
- **`--post-boot` has no Redis check** (#380), and this Redis logs to a file, so a journal-based check would read an empty pass.
- **run.md's Redis recovery point doesn't restore under `appendonly yes`** (#381), unless the RDB file is staged as the AOF's base.
- **A backup line's run can ship a stale snapshot, and the recovery point accepts it** (#382).
- **A held step's release can differ from the dry run's, and nothing records it** (#383).
- **The knob** (#384) has no line for a data store's own dependency (tailscaled). Nothing says a private caller in a public knob is #350's leak. An hourly quiet range takes 24 lines.

### Decisions

- **The backup line stood in for the dump,** after the owner's `SAVE`.
- **The owner didn't re-enable `default` or widen an ACL** to get past the refusal. Each `ACL LOG` entry the skill caused got its own not-a-fault row in the host's ACL docs.
- **The reboot was a root 0700 script mirroring the chain's steps,** each approved: the package-manager gate, stop Redis (which saves), the host's backup, `journalctl --sync`, `sync`, then the in-guest reboot. It was launched detached by `systemd-run --on-active=60 --timer-property=AccuracySec=1s`.
- **Tailscale was followed,** as its own held step after Redis.
- **The callers were told over one Mayfly channel.** All five answered with their reconnect bounds before any restart, and reported afterwards on the host's issue.

### Surprises

- **Established TCP connections survived the tailscaled restart:** each client's connection age dated it to the Redis restart before.
- **Redis logs `10000 changes in 60 seconds. Saving...` exactly 60 s after every start:** the AOF replay counts as changes. It isn't write load.
- **No group was lost, and that's what the per-group check is for.** Four of the five participants create their groups only at boot, from `$`, so a lost group would have skipped entries silently.
