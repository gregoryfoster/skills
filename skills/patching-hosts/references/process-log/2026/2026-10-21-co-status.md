## Session 2026-10-21 — co-status

This host's first run under the scripts (CannObserv/status#54, a public repo). It's the cohort's status monitor, which other hosts check in with, and it has a local Postgres.

### Environment

- exe.dev, `exe-dev-exeuntu`, generation `newer`, `guestd` layout. The journal is persistent. `/tmp` is under the `d` rule, so the boot keeps it. The platform kernel was a newer build after the boot than before it: the platform moved it, not the run.
- One local Postgres 16 cluster (`status`, `status_dev`, `status_test`), two uvicorn services, three oneshot timers (two sweeps every 60 s, an hourly drift check). No Redis, no Qdrant; Docker and nginx disabled.
- No knob before this run: the first probe was report-only against `automatic`.

### Readings

- **The first probe, with no knob:** 62 security (a lower bound), 26 `-updates`, Tailscale 1 pending. The apt timers were masked, with `Periodic::Enable "0"` from the image's `docker-disable-periodic-update`. The needrestart drop-in was already present. Tailscale's `AutoUpdate.Apply` was true on the node, although the owner had turned it off tailnet-wide.
- **The knob written:** `posture scheduled`, one window, an `inflight` over the sweep and drift units, two `service` lines, two `health` lines, a `datastore postgres` line for `status` and `status_dev`, `exception database:status_test`, and Tailscale's origin as `pin`.
- **The maintenance lane's dry run:** 88 packages, 176 s, 264 MiB, a 98 MiB download, no conffile prompts, no removals. No hold group was pending.
- **The bulk:** 90 upgraded, exit 0, 507 s (2.9× the dry run), 260 MiB; health 2 of 2 on the first poll. The two extra packages arrived with the bulk's own list refresh, 30 minutes after the dry run.
- **The reboot decision:** needrestart listed dbus, logind, journald, timesyncd, polkit, cron, packagekit, Postgres, both app services, the systemd manager and the user manager. PID 1 mapped 15 deleted files. There was no `reboot-required`.
- **The chain ran clean.** The API was down **11 s** (stop 19:11:18Z, active 19:11:29Z), and Postgres was back at the same second. `--post-boot`: every check green; the only finding was `setup-script:present`.

### What the skill got wrong or lacked

1. **The dry run counted against the host's own lists, which masked timers leave stale.** The first `probe.sh --lane maintenance --dry-run-into` counted **0**, and flagged `lists:stale` at 672 h: `unattended-upgrade --dry-run` read `/var/lib/apt/lists`, not the `--refresh-into` copy, and the host's lists were 28 days old. A 0 count makes the bulk refuse ("counted nothing"), so the run needed a host `apt-get update` before the dry run, which `run.md` §3 placed only inside the bulk. Proposed: the dry run refreshes the host's lists first, or refuses with that instruction when `lists:stale` is raised, rather than writing a 0-count summary.
2. **Tailscale auto-update: the tailnet default was off, and the node's own setting was on.** The owner had disabled auto-update tailnet-wide, but `tailscale debug prefs` read `Apply: true`: an explicit node setting outlives a tailnet default. The profile covered the reverse, the tailnet default re-applied over a node's off. Both directions need the node set too. After `tailscale set --auto-update=false`, it held through the reboot.
3. **The setup-script containment's first half has to precede the boot.** With the file absent between boots, `setup-script:redelivered` gives the remedy "once it's back on disk". The order that worked was CannObserv/provisioner#4's: `systemctl disable` before the reboot, `chmod 600` after it. The re-delivered file ran 0 times this boot, and came back at 0755. `--post-boot` names the key-shaped line, which is the useful prompt to revoke. The owner revoked the key (a Tailscale auth key) the same day, and the knob now declares `exception setup-script:redelivered`.

### Decisions

- **Posture `scheduled`** (monthly), both lanes in one window. Tailscale `pin`, not `follow`.
- **`status_test` was excepted rather than dumped:** the suite rebuilds it.
- **The deploy of the repo's own dependency bumps** (five Dependabot PRs) ran after the post-boot checks, in the same window, so the reboot and the deploy restarts weren't stacked.

### Surprises

- **`/tmp` held 115 leftovers from the host repo's own test suite:** a test that fails every `rm -rf` also fails the deploy script's EXIT-trap cleanup. `environment.tmp.staged` was the only reading that surfaced it (CannObserv/status#53).
- **The dump-copy hint** (`ssh <host> 'sudo cat …' > file`) worked as written; the owner's copies matched on the first try.
