## Session 2026-10-20 — host 6

Host 6 is in a **private** repo, so this entry names no identifier from it. This was its first monthly run under the scripts, after its step 0 hand run ([2026-09-28](2026-09-28-host-6.md)). It's a **primary with local Postgres and Redis and an ephemeral worker fleet**:
- an app restart fails every job in flight;
- one warm worker VM is always up;
- Redis binds the tailnet address.

There were two runs in one window. The second took 3 security updates that were published during the first.

### Environment

- exe.dev, `exe-dev-exeuntu`, markers `may-2026`, the `exe-init` init-only layout. `/tmp` is emptied at boot (`D`). The journal is persistent, reaching back 43 days.
- **Postgres 16:** one production database, plus 9 test-suite databases, one per xdist worker.
- **Redis 7:** `requirepass`, plus an **inline `user default` line** in `redis.conf`, and no `aclfile`.
- A nightly create-only Postgres dump to object storage (the host's backup regime). A liveness timer every 5 min.
- Posture `scheduled`; window Tue 16:00–22:00 UTC.

### Readings

- **The knob**, committed for this run:
  - two `inflight` lines: jobs neither pending nor terminal, and assigned workers. **Never the warm pool**, whose floor of 1 would make `inflight` print 1 forever;
  - five `health` lines: the app's database and broker flags (not its overall status, which a fleet credential fault also degrades), `pg_isready`, an anonymous `PING` refused, a non-loopback Redis bind, and a 2 GB disk floor (#390);
  - `depends redis-server tailscaled`, and Tailscale `follow` with its own hold;
  - a fleet section, `class ephemeral`.
- **The first probe had 24 findings:**
  - `database:` ×9: the test databases, excepted one line each (#455);
  - `restarters:unread:` ×5: `python -m` timer services, excepted `not-restarter:`;
  - `restarter:` ×6: units whose `OnFailure=` notifier is a `python -m` module. They had no exception, so they stayed open (#420; and #393 for the label);
  - `ordering:` for the app on Redis: fixed with `After=`;
  - Tailscale unscoped and unpinned ×3: fixed with the profile's pin file;
  - `tailscale:auto-update` true: off on the node and for the tailnet.
- **The pending set:**
  - security 50 (exact), `-updates` 56, Tailscale 1;
  - ESM 26 esm-apps, not attached;
  - language: the release tree's `uv.lock` couldn't be audited, being root's (#456). A frontend lock is one the probe doesn't audit.
- **The maintenance dry run exited 1:** fwupd at a conffile prompt (the image deleted its motd conffile), the profile's known case. The owner held it (`held:fwupd`), as wslcb did, and the dry run passed: 105 packages, 238 s.
- **The recovery point's first attempt refused** the Redis dump: "its aclfile sets the users", on a Redis with no `aclfile` (#458). The probe hadn't predicted it. A `systemd-creds` credential for `default` on the `datastore` line fixed it. Then the backup unit stood in for Postgres, and the owner attested the Redis RDB.
- **Run 1, the maintenance lane:**
  - the bulk took 104 in 629 s (2.6× the dry run), auto-removed nothing, and restarted nothing;
  - `redis`: the postinst restarted Redis cleanly. The app and the warm worker reconnected;
  - `tailscale`: matched the dry run's release, and the daemon matched the client;
  - a reboot was certain: PID 1 mapped deleted files, and dbus, logind and Postgres were listed;
  - the chain ran clean, down 24 s. Post-boot 19 of 20 (below).
- **3 security updates were published at 16:07Z,** while the bulk ran: the xz library family, which PID 1 and both data stores map, and the CA bundle.
- **Run 2, the security lane, the same evening:**
  - a new run directory was required, by design;
  - a new recovery point, which **couldn't use the backup unit after the boot** (#459);
  - the bulk took 3 in 25 s;
  - the run's own hold on Tailscale was released by a held step that installed nothing;
  - reboot, down 14 s. Post-boot 19 of 20.
- **Left pending after both runs:** 0 security, 0 `-updates`, 1 third-party (a newer Tailscale, for the next month's run), ESM 26.

### What the skill got wrong or lacked

- **Exact-match `database:` exceptions** for disposable per-worker test databases (#455).
- **An `OnFailure=` notifier the scan can't follow had no exception route.** A template among the hooked units can't even be declared a `restarter`: `systemctl show` refuses a bare template name, so `apply.sh` would refuse every step (#420).
- **A root-owned release tree's `uv.lock` is never audited** (#456).
- **A Redis with an inline `user` line:** the refusal names an `aclfile` that isn't there, and the probe doesn't warn before the recovery point (#458).
- **A backup regime can't stand in after any boot:** it's judged from systemd's state, which a boot resets, and the message reads "ended in success, so it isn't one to rely on" (#459).

### Decisions

- **The owner approved the sequence once,** to stop at the first red result, rather than step by step.
- **fwupd was held**, as on wslcb; a prune candidate.
- **The mid-run security updates were taken the same night,** so that no security update was left pending.
- **The warm worker was kept through both reboots:** it reconnected each time, as in step 0.

### Surprises

- **The platform kernel changed across the in-guest reboot**, to a newer build of the same series. It's consistent with the profile ("the platform's kernel"), but a reboot on exe.dev can bring a kernel nobody installed.
- **A security bulletin's packages landed between the bulk's list refresh and its end.** The run's own after-probe is what caught them.
- **The post-boot `containers` check fails for a build-cache container** (a buildx builder) behind a socket-activated dockerd. It's expected here, but the check can't tell a builder from a service container.
- **Neither reboot drew a liveness alert.** Each chain was launched to fire just after a 5-minute tick, and the app was back in under 25 s.
