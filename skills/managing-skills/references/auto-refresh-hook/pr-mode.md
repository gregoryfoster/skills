# The auto-refresh hook in `pr` mode ([#560](https://github.com/gregoryfoster/skills/issues/560))

Read this when a consumer sets `.skills/merge_mode` `pr`, or when debugging the hook there. The hook's other mechanics are in [the parent reference](../auto-refresh-hook.md).

A PR-only ruleset with no bypass refuses the hook's push to `main`, so the bump was rolled back every day and the pointer never advanced. With `.skills/merge_mode` `pr` ([#342](https://github.com/gregoryfoster/skills/issues/342)'s knob, read inline from the primary checkout) the hook never pushes to `main`. It proposes the bump as **one** pull request from `skills/submodule-refresh`, which later sessions update. Absent or `direct`, nothing changes.

- **The refresh still runs in place,** under the in-progress marker, with the same update, pins and post-bump doctor install ([#299](https://github.com/gregoryfoster/skills/issues/299)). The bump is then read into a private index, `.git/skills-update.pr-index`, and the content goes back to main's recorded pointer **before any network call**. Local `main` never moves, and when a run ends the content equals the pointer the index records ([#550](../auto-refresh-hook.md#a-rollback-undoes-the-whole-bump-550)). That is main's, unless a bump is staged with no marker (a hook from before #555, or a human's own `git add`). The hook never unstages that, and this mode never commits it, so the run names it on stderr with the `git reset` that clears it. The content stays on the staged pointer rather than HEAD's, so a human's bump keeps the content it was staged with. Fetching inside each submodule and writing the new gitlinks without checking them out was rejected: it re-implements `--remote --merge --init` and the pins, and cannot run the new pointer's own doctor installer.
- **The commit sits on a freshly fetched `@{u}`** (a fetch, never a pull), changing only the hook's paths. An operator's unpushed work is never in it, and a squash-merged PR is never carried twice. Where `main` and `@{u}` disagree on those paths, or on `.skills/skills-pin` (a merged refresh PR not yet pulled), there is no bump, and stderr says to pull.
- **The branch is replaced, not appended to,** with `--force-with-lease` against the tip `git ls-remote` just read. A PR is created only when none is open. An unchanged bump is not pushed again. An open PR whose branch carries a commit the hook did not write, such as a human's config fix for the new skills, is left alone.
- **Closed unmerged is a no.** A closed PR whose bump is the one this run would propose is not proposed again. The next upstream change is. `.skills/skills-pin` holds a submodule for good. A closed PR's head this clone never had (another clone proposed it, or gc pruned it after the branch was deleted) is fetched from `refs/pull/<n>/head` before comparing. If that fetch fails, nothing is proposed that run and stderr says so; the next day's run checks again.
- **What it needs, checked before the refresh moves anything** ([#576](https://github.com/gregoryfoster/skills/issues/576)): `gh` on `PATH`, an upstream for `main`, and a token for `gh`. The token is looked for in this order:
  1. `GH_TOKEN` (or `GITHUB_TOKEN`) already in the hook's environment;
  2. `GH_TOKEN` in the checkout's `.env`, or in the primary checkout's `.env` from a linked worktree. It is parsed as data with shipping-work's `load_env` grammar, never sourced;
  3. `gh`'s stored login (`gh auth token`, which reads it offline).

  A SessionStart hook runs beside the others, so another hook's export never reaches it. That is why the hook reads the `.env` itself. A `.env` token is handed to each `gh` call, and to an https remote's network `git` calls, in that call's environment only. It is never exported: the refresh runs the new pointer's own `install-doctor.sh` before anyone has reviewed the bump, and the token must not reach it. Don't prefix the hook's `settings.json` command with `GH_TOKEN=…`, which hands the token to that installer. The `.env` outranks the stored login, because a stale `hosts.yml` fails as a 401 that reads like a bad token (#334).
- **The repo `gh` is given** is `--repo <host>/<owner>/<repo>`, taken from the configured URL of `main`'s upstream remote. This pins the PR's base, where `gh`'s own choice among remotes could pick a fork parent. An SSH host is an `ssh_config` name, so it is resolved through `ssh -G`. That way a deploy-key alias such as `git@github-processor:o/r.git` (`Host github-processor`, `HostName github.com`) gives `github.com`, and SSH-over-443's `ssh.github.com` counts as `github.com` too. When `ssh -G` can't name the host, the hook omits `--repo`, `gh` resolves the repo from the checkout, and the log says so.
- **An https remote's fetch, `ls-remote` and push** get `gh auth git-credential` as a credential helper for that host, after any the consumer has configured. A host whose token lives only in the `.env` or in `gh`'s login can then push the branch without its own helper. The hook adds it through `GIT_CONFIG_COUNT`, which needs git ≥ 2.31, and skips it when the caller has already set `GIT_CONFIG_COUNT`. An SSH remote pushes with its key as before.
- **Reported once, never retried.** `gh` missing from `PATH`, no token from any of the three sources, `gh pr list` failing (a token GitHub rejects), or the branch push refused: one stderr line, then the run ends. A refusal by a rule names it (`GH013`, `GH006`); a lease lost to another clone's push is the same. The pr path runs only behind the day's lock, so "once" is once per UTC day per checkout.
- **A kill anywhere converges.** The marker carries `mode pr`. Its heal restores the content and removes the private index, and unstages nothing, since this mode never stages in the checkout's index. Killed between the push and `gh pr create`, the next run finds the same bump on the branch, pushes nothing and opens the PR. A second session finds the marker's owner live and leaves.
- **A `direct` run's unpushed commit** is rolled back, not pushed or moved, and the PR path redoes the bump. HEAD moves by compare-and-swap, so two sessions reaching the pass together cannot roll back twice.
- **Present but unusable is never `direct`.** Another word, or an empty file, means no refresh and no push or rollback, said once a day.
- **The PR is opened with the operator's `gh`,** so CI runs on it as on any PR. Its commit is built with `git commit-tree`, so the consumer's pre-commit hook does not run on it; the PR's checks stand in.
