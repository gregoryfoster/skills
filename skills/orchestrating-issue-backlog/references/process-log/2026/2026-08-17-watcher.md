### The finding worth promoting: a byte-for-byte sync test on a file *outside* the repo

SKILL.md already carries "a generated artifact under a byte-for-byte sync test
is a hard bundle signal" (2026-08-10, `openapi.json`). This session hit the same
rule with an extra property that changes what the orchestrator must do.

`tests/deploy/test_installed_unit_matches_repo.py` asserts

```python
assert installed == REPO_UNIT.read_text()
```

between `deploy/watcher.service` and `/etc/systemd/system/watcher.service`,
skipping only when the unit is absent — and it is installed on the VM that runs
the agents. Two issues (#256 `SuccessExitStatus=143`, #262 the bus producer
gate) both edit that unit, so the bundle signal fired normally.

**But the pinned counterpart is a host-level file, not a repo artifact.**
`git worktree` isolates the repo and nothing else, so *every* concurrent agent's
test run reads the same `/etc/systemd/system/watcher.service`. That yields a
failure mode the 2026-08-10 version does not have:

- The agent editing the repo unit sees `test_installed_unit_matches_repo` fail
  **in its own worktree** — correctly, and unavoidably, since the installed copy
  still matches `main`.
- If that agent "fixes" it with `sudo cp`, it flips the **live production unit**
  mid-batch and turns every co-batch agent's run red on a file none of them
  touched.

So the brief needs a clause the openapi case never did: *expect exactly this one
failure; do not repair it.* The install moves to the orchestrator, after the
batch merges to main.

Generalized: **a sync test whose counterpart lives outside the repo is a shared
mutable resource on the Q5 axis, discovered in Step 5.** Worth grepping for
alongside the fixture-escape grep — same question ("what does the worktree not
clone"), different instrument. Candidate shapes: installed systemd units,
`/etc/` config, a global npm/pip install, a shared browser profile, a checked-in
hash of something the host generates.

Held as a log entry at one sighting rather than promoted; if a second project
hits a repo-external sync assertion, the Step 5 grep list should gain a line.

### Decide-then-rescore: five decisions, three resolved *against* the body

Step 4's decide-then-rescore gate did the heaviest lifting of the session. Five
of eight issues named an unresolved decision. All five were settled from
evidence rather than judgement, and the direction is the interesting part:

| Issue | Body's leading option | Resolved | Source of truth |
|---|---|---|---|
| #250 | archive ⇒ revoke, worried about a restore-race politeness gap | option (a), extended to `is_active=false`; **the feared gap cannot exist** | co-core `FetchPolicyState` docstring |
| #260 | "1 or 3, not 2"; "worth asking Archiver" | **3 + 2 together** | Archiver's own code answered the question |
| #261 | "(c) is probably the answer" | (c) confirmed ⇒ (a) safe | Archiver's `UniqueConstraint` |
| #262 | "Option 2 is probably right" | option 2, taken | — |
| #249 | (decision named, not surfaced by me pre-scoring) | **split** | issue's own sequencing |

Three observations.

**1. A dependency's *source* can settle a question the issue frames as open.**
#250 asks "worth confirming Replicator's LWW handling either way". The answer was
already in the installed co-core package, in prose:

> `revoked` is the tombstone — LWW has no delete. It means "**no explicit policy
> for this host**", *not* "no limit": the consumer falls back to its own
> conservative default.

plus rule 1, "a consumer's fallback default must be at least as strict as
anything the producer would publish". That does not merely answer the question —
it **inverts the risk model**. The issue feared revocation would drop a host's
politeness floor; by contract it cannot, and the *status quo* (publishing a live
`min_interval` for an unwatched host) is the only way that host ends up looser
than the fallback.

Generalizes to: **when an issue says "confirm with the consumer", read the
shared contract package first.** For a repo on a versioned shared core, the
vocabulary docstrings are a settled, checked-in design record — cheaper than a
cross-repo conversation and more authoritative than either side's issue body.
Already partly covered by Step 1-2's "read the artifact, not the body" clause
for *generated* artifacts; this is the same move for a *dependency's* artifact.

**2. Read-only sibling inspection settled two issues the cross-repo policy
forbids editing.** #260 asks whether Archiver always has specs in hand; #261 asks
whether Archiver can re-derive a mapping. Both answered in ~90 seconds by
grepping `/home/exedev/archiver`:

```
registry_announcement.py:156   if source is None or not source.source_specs:
source_revision.py:83          UniqueConstraint(info_source_id, content_fingerprint)
```

The repo's cross-repo policy bars *editing* siblings. It does not bar reading
them, and this backlog had two issues whose central open question was
"what does the sibling do". Worth stating explicitly, because the policy's
phrasing ("do not directly edit sibling repos") reads at a glance like a
don't-touch and I nearly deferred both questions as cross-repo.

**3. A decision I did not surface pre-scoring.** I told the user "four of the
eight name a decision" and then discovered while scoring that #249 does too
("`FetchCommandStatus.FAILED` is wrong for the row"). Had to add it as a fifth,
mid-gate. SKILL.md already says you cannot tell which issues need this until you
have scored them — that is exactly right, and the lesson is to phrase the count
as provisional when presenting rather than as a closed set.
