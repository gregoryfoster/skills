## Lessons

### 1. Q5 rung 1 was blocked by a role privilege, not by the naming guard

The skill's read-the-guard clause sent me to the suite's DSN safety check, which turned out to be
permissive — `"test" in dbname and "prod" not in dbname`, so `co_pm_db_test_a1` would pass and
per-agent slots were namable. Rung 1 still failed, one layer lower: `SELECT rolcreatedb, rolsuper`
showed the test role had neither, on a managed DO cluster where creating a database is a console
action by a human.

**Suggested skill change (promotable):** the read-the-guard clause should have a second half —
*then check the role can actually create the slots*. One query:
`SELECT rolcreatedb, rolsuper FROM pg_roles WHERE rolname = current_user`. A permissive guard plus a
non-CREATEDB role reads as "rung 1 available" right up until you try it, and the check costs one
round-trip during the interview instead of a failed provisioning step after it.

**Promoted (#249), as a relocation rather than an addition, and as the 3rd sighting.** The privilege
fact was already in the skill — "check whether the test role can create them — usually not, so it is
a one-time superuser step" — but inside resolution 1 of the ladder, a rung you only reach after
concluding rung 1 is available. 2026-08-07 usa-wa (`rolcreatedb=f, rolsuper=f`) and 2026-08-17
watcher (the `watcher` role lacking `CREATEDB`) are the two prior sightings. The session's real
finding is **placement**, and it is right: the sentence moved up into the read-the-guard bullet, which
had ended on "the ceiling reverts to the host's CPU/RAM limit" — the exact wrong conclusion this
session reached — and gained the one-line query.

### 2. Decisions at the decide-then-rescore gate changed the dependency *graph*, not just scores

Three issues carried a named decision. The skill frames this gate as a scoring correction ("moved one
issue from 14 to 16, another's blast Med→High"). Here two of the three decisions moved the batch
shape directly:

- #478 "report the claim on the wire" **created** an edge — it put #478 on `ObservationResponse`
  alongside #477, which is the entire reason #478 is gated in Batch B rather than parallel in A.
- #479 "approximate via winner subscriptions" (vs. recording the delete-time audience) **destroyed** a
  potential edge — the rejected option needed a schema change and would have put #479 on
  `schemas.py` too, making Batch A's three agents into two-plus-a-gate.

**Suggested skill change (promotable):** at the decide-then-rescore gate, ask of each option not only
"what does this score" but *"does this option create or remove a conflict edge"*. Two of three did
here, and both effects were invisible until the option was named — a Step 5 grep run before the
decision would have measured the wrong footprint in both directions.

**Promoted (#249), merged with 2026-08-23's prior sighting, which had not been promoted.** That
session is the same axis in the opposite direction: #228's decision removed it from `install-hook.sh`
entirely, dropping blast High→Med and dissolving the rationale that had bundled it while the bundle
itself survived on a different reason. Its lesson — re-derive each Q0 bundle's rationale after the
gate, because nothing goes red when a plan's stated reason stops being true — is the silent-failure
half, and rides in the same clause.

### 3. `git show --stat` on the commit that cites an issue number is the cheap rescope disambiguator

#473 was a rescope-to-residual: its title claimed three deliverables, one of which had shipped. The
skill's prescribed move is to grep the body's deliverables and each comment's separately. What
actually settled it in one command was reading the *commit that claims the issue number* —
`git show --stat d2f5ebb` showed it touched exactly one file (`.skills/context-seams-ok`), proving
the seam-judging half shipped and the other two halves had not been started. A body grep would have
found the seam list either way and left the ambiguity intact.

**Suggested skill change (promotable, small):** add to Step 1–2's closed-in-fact paragraph — when a
merged commit cites the issue number, read its diffstat. A commit that names the issue and touches
one file of a three-deliverable issue is direct evidence of *partial* delivery, which is the
disposition the body grep is worst at detecting.

**Held (#249), pending a second sighting.** No prior sighting anywhere in the 2026 log, and it
sharpens a detector the skill already prescribes rather than introducing a rule. It sits near the
2026-08-17 #161 bar ("promote what defeats a detector the skill already prescribes") without landing
on it: the body grep on a partially-shipped issue returns hits and reports the wrong *disposition*,
where #161's two candidates made an existing check report **success** under the failure. The
technique is sound; the promotion needs the recurrence.

### 4. A provenance sub-shape: consumer-dialogue-derived

Four of the five issues came out of one GitHub thread with an external producer — a single dialogue,
not a review pass. The behaviour matched the CR-surfaced prior (naturally disjoint: 3 of 4 code
issues fully parallel) and the "across-the-stack → disjoint" half of the feature-followup heuristic,
because a consumer reports one defect per surface they hit: an audit script, an API response
contract, a core write path, a change feed.

**Not suggesting promotion** — one observation, and it may just be CR-surfaced wearing different
clothes. Recording it so a second sighting can confirm or kill it.

### 5. A named section can be too coarse an ownership unit — bullet-level, with a no-restructuring clause

One contested doc file inside a batch, resolved by bullet-level ownership
(`docs/API_ASSIGNMENTS.md`: one agent owns a single bullet, the other owns the rest of the file) with
an explicit no-restructuring clause. Step 5's rule is to own a **named section** rather than a line
range, precisely because Markdown line numbers go stale (2026-08-17 watcher within a batch,
2026-08-17 skills across them). Here the named section was the wrong granularity in the other
direction: the `^###` map pointed at one section both agents needed, so ownership had to go a level
finer than the rule's guidance suggests.

**Held at one sighting**, but recorded under its own heading rather than as a note, so a second
sighting finds it by grep. The generalization it would support, if confirmed: the rule's governing
property is still "do the windows overlap" — a named section is the *default* unit because it
survives edits above it, not because it is the smallest safe one, and a section both agents need is
the signal to subdivide rather than to sequence.
