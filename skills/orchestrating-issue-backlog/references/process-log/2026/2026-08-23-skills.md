## What this session is for

### Adoption-feedback decomposes on the owning file — and the *decision* can move which file that is

The skill's prior on adoption-feedback backlogs held: seven issues, two script
families, near-total pairwise file sharing, and the agent unit fell out of "who
owns this file" rather than "how many issues are there." Nine issues → five
agents.

But one owner changed **at the decision gate, not at the grep**. #228 was filed
against `HOOK_COMMAND` in `install-hook.sh` — a third claimant on the most
contested file in the backlog. Choosing prose-only over the self-guarding
registered command removed it from that script **entirely**. Blast High → Med,
and the three-way contention on `install-hook.sh` became two-way.

It stayed with the same agent anyway, but for a **different reason than the one
that put it there**: #227's recipe documentation and #228's first-session note
land in the same section of `code-exploration-policy.md`. The original
rationale (all three interleave in `--check`) dissolved and a new one replaced
it.

**The lesson is about ordering, not about #228.** Q0 bundles agents; the
decide-then-rescore gate runs *after*, and can invalidate the footprint the
bundle was built on. Re-derive each bundle's rationale after the gate rather
than assuming the grouping survives its own justification. Here the grouping
survived and the reason did not — which is the case that fails silently,
because nothing goes red when a plan's stated rationale stops being true.

### An orchestrator's instrument is the claim most worth auditing

#223 predicts *"expect the first run to be the interesting part — 28 links have
never been checked."* The sweep reported **three broken anchors**, which read as
confirmation with a smaller number.

It was wrong. The slugifier collapsed `\s+` to a single hyphen instead of one
hyphen per space, so every em-dash heading mis-slugged — `### Phase 5d —
Provision PostgreSQL` produces `phase-5d--provision-postgresql`, keeping the
double hyphen the stripped em dash leaves behind. Corrected: **27 anchored
links, 27 resolving.** The one non-resolver is an illustrative fragment inside
prose that the implementation must *exempt*, not repair.

This is the 2026-08-12 lesson recurring, and worth logging because the failure
mode was **inverted** from that one. There, a loose regex over-reported and the
correction was retracted publicly. Here the wrong instrument produced a number
that *agreed with the issue's prediction* — three breaks where the body expected
breaks. A wrong instrument that confirms the body is far harder to notice than
one that contradicts it, because contradiction is what triggers a second look.
The check that caught it was mechanical rather than suspicious: read the actual
headings the two "broken" anchors point at.

**Practical form:** when a sweep confirms an issue's prediction, verify one
positive by hand. Confirmation is when the audit is least likely to happen.

Note the pattern across the three: none was stale in the sense of *another
commit moved the code*. Each was wrong **at filing time** — one over-predicted
from an unverified hedge, one under-read its own repo's docs, one proposed a
mechanism a later decision would discard. Staleness-with-batch-depth is the
familiar decay mode; **wrong-on-arrival** is a separate one, and the closed-in-
fact grep catches it only if run against every issue rather than the
suspicious-looking ones.

### A verification-mode asymmetry with no config change behind it

The established form of this rule involves an agent changing the test runner's
*configuration*, so the orchestrator's post-merge run is the first under the new
mode. #223 produces the same asymmetry with **no config change at all**: it adds
the first check in the repo's history that resolves `skills/**/*.md` anchor
fragments, and two co-batch agents write markdown into its scope.

Every Batch A agent verifies under a suite that does not yet check anchors. The
`batch/a` run is the first under the new one. The mitigation is an **ordering
constraint chosen for attribution rather than safety**: A4 merges last, so a red
gate reads unambiguously as "the new check meeting new prose" instead of as the
defect of whichever agent happened to merge before it.

Worth generalizing: any agent whose deliverable is *a new check over other
agents' output* creates this asymmetry, whether or not it touches
configuration. Detection is unchanged either way; **attribution** is what the
merge order buys.

### A semantic dependency edge with no merge conflict to announce it

#224's chosen shape — a per-skill `.install` manifest holding each hook's
`install-hook.sh` arguments — makes A3's new files a **transcription of a script
A1 is editing**. If #227 adds a flag, the manifests go stale. Nothing conflicts
textually; both agents' files are new or untouched by the other.

Same class as the shared-fixture edge, reached by a different route: not a
runtime dependency but a **content** one, where one agent's file quotes another
agent's interface. Named in the design doc with an instruction to A3 to read the
merged `install-hook.sh` before signalling, since no automated check will say so.

## Decide-then-rescore

Three issues arrived at Scope 1–2 because each named an unresolved decision in
its own body — #220 (three contract options), #224 (two repair-line shapes),
#228 (three fixes plus an unanswered factual question). All three answered at
the gate; all three re-scored up; #228 also changed blast class. Fourth
consecutive session where this gate moved the plan rather than confirming it.

**#228's factual question was not answered — it was assigned.** Does Claude
Code run a `SessionStart` event's matching hooks in parallel or sequentially in
array order? Two skills currently prescribe a layout implying that ordering
helps. An orchestrator guess here would propagate into two skills' prose, so the
brief tells A1 to verify it and write down whichever is true. **Not every
decision surfaced at the gate is the user's to make; some are the tree's, and
the gate's job is to stop a worker from guessing rather than to supply an
answer.**

### The baseline rule from 2026-08-21 paid for itself immediately

That session's headline was *"journaling the session invalidated the baseline it
then briefed — the Step 10 entry added 3 parametrized tests; measure after
committing the plan."* Followed here, and it fired again with the same
arithmetic: `8ee142a` read **3038 passed**, and after committing this plan plus
this entry, `76263fd` reads **3041 passed**. Three tests, from the journal.

The mechanism is worth stating plainly because it is specific to this repo and
invisible from outside it: **the process log lives under `skills/`, so it is
inside the collection scope of the structural suite it is describing.** Writing
about a session mutates the number that session is measuring. Briefing 3038
would have had all four workers stop and report a mismatch against a tree that
was entirely correct — Rule 3's detector firing on the orchestrator's own
bookkeeping, and the most expensive kind of false positive, because the correct
response to it is to halt.

Second consecutive session; promoted from "a thing that happened once" to
standing procedure: **commit the plan and the journal, then measure, then brief.**
