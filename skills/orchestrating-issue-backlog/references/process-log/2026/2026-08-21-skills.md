### The lesson: measure the *recommendation*, not only the claims

#217 named three options and recommended option 2 — assert
`worst_case_exact()` against the ratchet — calling it "the strongest option: it
makes the always-on gate correct rather than adding a second gate." The
reasoning is sound. The body simply never ran it.

Running it took one script and about ninety seconds. It fails **7 of 19 skills
today**, requiring ~8,100 tokens of trimming, including 3,410 from
`orchestrating-issue-backlog` — the file whose own ratchet comment refuses
exactly that trade in as many words: *"A ratchet that forces a runbook to omit
the rule its own instruction needs is optimising the wrong quantity."*

The skill already says *a grep sizes a surface; only execution measures a
behaviour*, and *an issue body's own hedge is a grep target*. Neither quite
covers this. #217's body was **confident and unhedged**, and the falsifiable
thing was not a claim about the current tree — it was a **prediction about the
blast radius of its own prescribed remedy**. Worker step 5 tells the implementing
agent to verify prescribed implementations, but that is too late by one stage:
an agent discovering mid-batch that its issue's remedy requires editing seven
other skills has already blown the batch it is in.

**The rule this suggests:** at the decide-then-rescore gate, when an issue
recommends one of several options *and* the recommended option's cost is a
repo-wide quantity, measure it before adopting it. The measurement is what turns
Scope 1 into Scope 3; adopting the recommendation unmeasured is what turns Scope
1 into a Batch B nobody planned.

Two details worth keeping:

- The option was **cheap to measure precisely because the machinery existed**.
  `worst_case_exact()` is already implemented at `test_skill_self_budget.py:422`
  — used only to *format the failure message*, never as the assertion. A dry run
  was nineteen calls to a helper the repo already ships. Look for that before
  concluding an option is expensive to evaluate.
- **The option was not rejected on merit.** It becomes correct the moment those
  seven ratchets come down. That distinction went into the issue comment as a
  pointer rather than a deletion, so the next reader does not re-derive it.

### Second lesson: hunt the assertion that stays green, at plan time

`test_socraticode_policy_split.py:353` pins the generated doc's Graph health
section **as concepts** (`unresolved`, `call edge`, `corrobo`, `re-index`) and
deliberately not as a sentence. That design is right — a sentence-level pin
would fight every legitimate rewording.

It also means #216's reword of the driver string leaves the test **green while
the doc goes stale**: `socraticode-doc.md:124–126` quotes the current string
verbatim, the test's own docstring at `:356` quotes it again, and nothing
asserts that the doc's quotation matches what the driver emits.

The skill's existing clause (2026-08-14 observo) says to grep for assertions the
fix makes *vacuous*, not only the ones it breaks. This session applied it
**proactively during Step 5** rather than discovering it post-merge, and the
question that surfaced it was mechanical: *for each string this fix changes,
which assertion mentioning it will still pass?* A **deliberately loose pin** is
the highest-yield place to ask — the looseness that makes it robust to good
rewordings is exactly what makes it blind to a reword that leaves a quotation
behind. Closing it became a line of A1's brief.

### Third: a read-only constraint derived from another agent's new gate

`init-socraticode/SKILL.md` sits at 9,758 estimated against a 10,050 ratchet —

Budget-as-invisible-conflict is well established here (2026-08-16, 2026-08-18).
The new shape is the *direction*: not two agents contending for one budget, but
one agent's read-only constraint derived from **another agent's not-yet-merged
gate**. The edge is only visible if you compute the batch's own arithmetic
against the change one of its agents is making. Handled by brief, not by a gate —
`references/socraticode-doc.md` had 6,778 tokens of room.
