## Lessons

### 1. The batch table dropped one of twelve work items, and nothing downstream could see it

At Step 7 the orchestrator reshuffled batches B and C to bring higher-scoring items forward.
That left eleven slots for twelve items, and #574→#572 fell out. The table still read as
complete — six batches, plausible gates — so the omission went on through
everything written from it: the design doc's table, the tracking issue rendered from the
design doc, and the per-issue scheduling comments. It surfaced only when the orchestrator
enumerated the work items by hand while drafting those comments. All three have since been
corrected, and #580's scope lists #574→#572 in Batch C.

**Promoted ([#291](https://github.com/gregoryfoster/skills/issues/291)), as one sentence at
the end of Step 7, with the detail in [`batch-design.md`](../../batch-design.md).** It is a
count because the table looked right, and only a number could be wrong in a way anyone would
see. This is the second sighting. The comment on #291 supplied the first from the
execution side: the 2026-09-14 plan's "16 work units" was its wave grid, the run produced
fifteen workers, and the number reached an upstream issue before anyone counted (corrected
in both entries). That comment also pointed out that a check comparing the table with the
backlog could pass beside a wrong summary line. So the promoted form carries the reconciled
number forward for the design doc and the tracking issue to quote, rather than only asserting
equality. 2026-09-16 wordpress had already run the count (13 = 3+3+3+3+1) and found it cheap.

### 2. Greedy score-order pairing stranded the item; a constraint solve placed it

#574→#572 shared a source or test file with 4 of the other 11 work items — the
`worker_manager.py` and `jobs_api.py` exclusion groups, with #567, #571, #577 and #579. After
the reshuffle no slot could take it, and a greedy pass had no way to notice. Re-solving the
assignment as "every pair file-disjoint under the gates" placed all twelve in the same six
batches with no extra boundary. The plan records the pairing as the only assignment that
satisfies that rule for all twelve items given the gates.

**Promoted ([#291](https://github.com/gregoryfoster/skills/issues/291)) into
[`batch-design.md`](../../batch-design.md), beside the count.** One sighting, admitted
because the failure it prevents is lesson 1's and a count only detects it. The "about a
third" threshold is #291's, drawn from this one item with edges to 4 of 11. It is written as
an order of *assignment*, not of batches, because the stranded item ran in the third of six.

### 3. The briefed baseline was carried from one tree to another

The main checkout measured 4550 passed / 27 skipped. #291 was filed at 15:00 UTC, before
Batch A had reported, and its table gave the worker worktree 4548 / 29, since two tests
guarded on a vendored path skip where `skills-vendor/` is uninitialised. That number was inferred from
the known cause, not measured, and it was wrong too: both Batch A workers measured
**4547 / 30**. The third skip is `test_app_imports_without_static_build.py`, because a
worktree has no built `static/dist` bundle. The collected total was 4577 either way. Both
workers reported the mismatch rather than reconciling to it, which is Worker step 4 and the
report-back slot doing their jobs, and every later gate reconciled exactly.

**Promoted ([#291](https://github.com/gregoryfoster/skills/issues/291)), as a sub-bullet
under Rule 3's baseline obligation in [`execution.md`](../../execution.md):** measure in a tree cut
the way the workers' are, and name any expected delta and its cause in the brief. That is
the issue's proposal. What happened after it was filed sharpened it, because the proposal's
own table carried the inferred number, so the rule also forbids adjusting the main
checkout's count for causes you know of. It is promoted at one sighting because it turns a
prescribed detector against itself: Rule 3's stop condition fires on every worker it exists
to protect, and one that fires on every worker teaches everyone to discount it.

The plan's outcome recorded one further reading, **held** here: re-run with `-rs`, the same
worktree reported 4740 passed / 32 skipped against its own final gate's 4739 / 30, so the
executed count is sensitive to the environment even at a fixed tree.

### 4. The baseline gap found an issue that could not be verified where it would be worked

One of the two submodule skips was
`tests/shared/test_doc_sensitive_paths_audit.py::test_no_entry_is_dead` — #578's own
acceptance guard. A #578 worker would have seen it skip and reported green without the
census ever running. The plan named it under Key decisions as a verification-mode asymmetry,
told the worker that a green worktree run was not evidence for #578, and scheduled a
main-checkout re-run of the guard at the gate. The plan also kept the worker off
`git submodule update --init`, on the stated ground that linked worktrees share
`.git/modules/`; that ground is not verified here and was not promoted.

**Promoted ([#291](https://github.com/gregoryfoster/skills/issues/291)) into
[`batch-design.md`](../../batch-design.md), pointing at Step 8's key decision.** Step 8's
example of the asymmetry is a worker that changes the runner's config. 2026-08-27 (#240–#244)
logged a guard that an opt-in tier skips everywhere. This guard runs in the main checkout and
skips only in worktrees, so the measurement Rule 3 now asks for is also what finds it.

## Confirmations and log-only notes

- **A decision taken at the gate is a hypothesis** (2026-09-15 promotion), second sighting.
  Five worker corrections would have shipped defects, and three of them were the
  orchestrator's own. #568's recorded fix was already in the tree verbatim — it *is* the
  bug. #577's recorded decision was unimplementable, since `build_setup_script` writes only
  `_AGENT_RUNTIME_ENV_KEYS`. #575's brief put three registries in the wrong file. **Carried.**
- **The decision that licensed a pairing was itself falsified.** #577's decision is what kept
  it out of `fleet_manager.py` and let it pair with #563. It was also the one the worker found
  unimplementable, and the worker shipped a route through neither of the two channels the
  brief named. A pairing inherits its decision's reliability. **Held** at one sighting.
- **Blast ≠ priority, two variants at once.** #578 (score 10, conflicting with nothing) filled
  the slot that would otherwise have idled, in the last batch. #579 sequenced last on
  epistemics and was vindicated: after fourteen merges, 7 of its claims held, 2 held but were
  understated, and 1 was never true. Its filed seam census was off by 8.5×. **Carried** — Key
  Principles.
- **A carry-in written in two places.** The `claim_warm` fix went into both #563's issue
  comment and Batch D's brief. D shipped it, the comment was never retracted, and #563's worker
  read a stale instruction and correctly declined it. **Held** — a handoff (Orchestrator step
  5) needs one home.
- **The doc budget went unbriefed.** Four live docs went over the 10,000-token budget during
  the run (CannObserv/observo#584), all of them under it on `main`. `batch-design.md` already says to
  measure every token-gated file at Step 5, and this run did not. **Carried** — a miss of an
  existing rule, not a new one.
- **Disk halted a worker.** The host reached 0 bytes free mid-batch, with a private venv per
  worker, and that worker reported 42 failures and 74 errors, all ENOSPC. This is the second
  time disk has bound (2026-08-13 cli: ~662 MB `.venv` per worktree). **Held** — Q5's capacity
  half already asks what one host running every worktree can bear.
