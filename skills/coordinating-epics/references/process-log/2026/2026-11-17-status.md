## Session 2026-11-17 — CannObserv/status#71

A backlog epic on the cohort's monitoring service: a public FastAPI dead-man's-timer API with a 60 s sweep, alerting through the cohort's notifier. It was coordinated in one thread for 21 days, from creation on 2026-10-27 to parking-lot mode on 2026-11-17. The thread outlived several context compactions. The epic body and a scratch directory of ops files and briefs carried the state across each one, and the scratch directory itself vanished once. This host's first run is [2026-10-13](2026-10-13-status.md).

### Shape

- **Way in:** a backlog plus the operator's one-line rule, reused from the first run: sibling requests first, then bugs, then smaller work. It had 7 items at creation (2 sibling monitor requests and 5 Dependabot PRs), all slotted, none parked, no closures.
- **Children:** 47 ticked at the park, and one owed (a tick waiting on a dated event). About 40 arrived during the run:
  - 12 sibling requests: disk-headroom and patch-due monitors for other hosts, a retirement, a repoint, and an SDK adoption filed from the sibling's side;
  - 5 refresh-hook PRs;
  - 2 rounds of Dependabot, 6 PRs;
  - about 15 follow-ups born in review or close-outs, which the operator chose to file at check-ins.
- **Check-ins:** 35 operator check-ins, plus 31 scheduled 6-hourly ticks.
- **Ending:** the exit criterion (the 7 items) was met on day 1. The epic then ran in intake mode, and parked when the last known child landed.

### What was different

- **Sibling requests were most of the work.** Each disk-headroom monitor followed one shape: create disabled and post the id, wait for the consumer's first `ok`, enable, rehearse an alert through both channels, then close on the operator's channel confirmation. The fastest went from id to cleared in 14 minutes.
- **Refresh-hook PRs were children by an operator override:** next in line, ahead of bugs, because they set how every other thread works. The hook rewrites its PR in place at the first session of each UTC day, so each one was merged with `--match-head-commit` at the head that was reviewed.
- **Peer sessions messaged the coordinator directly.** One closed its child on the owner's call and left the coordinator to record a dated event: the first scheduled run of a new GC version, captured in the background at 05:34Z.

### Findings

**Scheduling**
- **S1. A recurring session cron expires silently after 7 days, and the epic went on claiming it.** The exit criterion said "the coordinator thread scans every 6 h". The ticks ran from 2026-10-28 to 2026-11-04 12:47Z and then stopped. For 13 days nothing said so, and new items were found only at operator check-ins. Write the cron's expiry into the epic when you create it, and say at every check-in whether the job is still listed. The operator's replacement at the park: one non-recurring job 12 h out, deleted and re-created at the end of every check-in, operator-driven or scheduled. [replicator's 2026-11-16 run](2026-11-16-replicator.md) used the same 12 h reset for its idle check (its "What was different"), so this is a second run: a promotion candidate.

**Pre-flight**
- **S2. Check that the test path reaches the thing at all.** Four children turned on it:
  - the ship gate's import check had skipped on every run, because it guessed a package name that doesn't exist (a review had counted it as passed);
  - every API test overrode the session dependency with a fixture, so a cancellation test through the usual client would have tested the override;
  - moving to an HTTP library that verifies against the OS trust store would have left a certifi-bundle guard passing over a bundle no call read. The OS store still trusted two roots certifi had dropped, so certifi was kept explicitly;
  - the same move would have stranded a log-redaction filter on the old library's logger, where it masked nothing.
- **S3. Trace the worry before briefing it.** An issue asked whether installing pre-commit would slow the refresh hook's commit. In PR mode the hook builds its commit with `git commit-tree` and never runs `git commit`, so it can't. The brief said so as `[traced]` and asked the implementer to confirm. They did.
- **S4. Read a cut query's row count.** A pre-flight read a 3-row fault query as 2 and missed a standing fault on the channel pair a new monitor would use. "Count the rows, don't trust a cut output" went into the epic's Watching block for every later pre-flight.

**Verify**
- **S5. Hold the tick on evidence that only comes after the deploy.** Twice the work was merged, deployed and green, but its "Done when" needed an event that hadn't happened yet:
  - the first real dispatch through the new HTTP library (none was sent for over 3 h after the deploy);
  - the first refresh-hook run after a hook install (next UTC day).

  Both stayed unticked, with the owed event, its expected time and the check written in Watching. The first was ticked at the next check-in on three `succeeded` dispatches.
- **S6. A refresh-hook PR merged with no review or close-out gets the coordinator's own checks:** CI by job on the head and the merge, gitlinks, doctor and refresh rc 0, and each linked reader. After that the brief asked for a close-out explicitly, and the next one had it.
- **S7. Dependabot bundle PRs on `uv.lock` stay CLEAN and never rebase themselves.** One sat behind `main` for days. `@dependabot recreate` (or `rebase`) moved it within minutes. A transitive advisory needed a floor in `[tool.uv] constraint-dependencies`, plus a guard test taught to read it. `uv audit` reproduced the advisory before Dependabot did, because GitHub's advisory database hadn't published it yet (it did at 16:43Z that day).

**The coordinator's own claims**
- **S8. 12 brief errors, corrected in place.** Most were things estimated or recalled rather than read in the posting command:
  - three timestamps ahead of the clock (fixed by filling every `[measured …]` from `date -u` in the same command);
  - a package count;
  - a line reference;
  - a token "bad" that only had a stray prefix in `.env`;
  - a flake mode inverted;
  - a status code;
  - "weekly" for a daily timer;
  - a missed path in a commit range;
  - a "first time" claim another host had already made;
  - the cut query (S4).

  Each was marked visibly and searched for wherever else it was made.
- **S9. A sibling's changelog cited the wrong issue for its own change.** The coordinator noted it in the brief and didn't correct it on the sibling's repo, because that needs the operator's consent.
