## Session 2026-11-14 — CannObserv/power-map#598

This entry continues [2026-10-02-power-map.md](2026-10-02-power-map.md). That entry covered creation and the first three check-ins. This one covers the run to its close on 2026-11-14.

The run was a burn-down of power-map's open issues numbered #481 and up, after the usa-wa dataset-subscription cutover. The operator's rule was *"prioritize bugs and smaller workstreams"*. It was adopted onto this skill on 2026-10-15 (CannObserv/power-map#661). Bare `#N` refs below are CannObserv/power-map's. The host is a FastAPI service with managed Postgres, about 14 systemd timers, and one VM that both serves production and runs the development worktrees.

### Shape

- **Dates:** 2026-10-01 to 2026-11-14, 45 days.
- **Check-ins:** about 80 log lines. Several days had two or three check-ins, and two gaps ran four to five days.
- **Children:** 18 open issues at creation. At the close the body held 88 lines done and 2 out of epic. 94 issues numbered #481 and up closed in the window.
  - Most of the growth came from follow-ups that implementers filed, or that the coordinator harvested from run records.
  - Dependabot rounds were folded into one issue each, at the operator's call.
- **Releases:** from v0.57.2 to v0.70.1, about 30 tagged.
- **Exit criterion:** every open issue ≥ #481, and every one filed during the run, is closed, parked with a written trigger, or in an Ops lane the operator owns.
- **Ending:** the operator asked for close-out once the last tiny child shipped. The two Ops items went on as standalone issues, and one dated aftercare was filed (P2 below).

### What was different

- **An Ops lane with no implementer.** Operator-owned items sat in their own section, with their own exit clause, all run: an exe.dev support question, a host patch adoption, a disk-GC adoption. Two of them were still open at the end, and the epic closed around them.
- **Merge mode changed mid-run** (2026-11-09). From then on, all work reached `main` through PRs, the skills auto-refresh hook included. Hook PRs arrived as new numbers that every check-in had to slot. The editor's rule that the body must name each new number caught all of them.
- **Implementers left issues open "for the coordinator".** It became a convention: the implementer merges, deploys and posts the record; the coordinator verifies and recommends; the operator says "close". Many issues took that extra round-trip.
- **The operator asked for an Ops item early,** and spotted a missing issue that the accounting check couldn't see (A1).

### Findings

**Accounting (A)**
- **A1:** a line naming two issues (`#716 + #712`) was ticked when the first closed. The second issue's last clause was carried onto a third child. When that child closed, nothing closed the second issue. Three weeks later the operator asked why #712 was missing. `--account` passed throughout, because the ref had a line. **Candidate:** `--account` flags a ticked line whose refs aren't all closed. From this run only.
- **A2:** the verify recipe went stale. It said "no GitHub CI" for a week after a child added a PR workflow. The recipe is state: a child that changes the verify surface updates the recipe in the same write. A related fact the recipe needs: a `pull_request`-only workflow leaves `main`'s merge commits with no check-runs, so read the PR's head SHA. From this run only.

**Parking (P)**
- **P1:** a parked option with a measured trigger closed cleanly. #796 was parked with a read-only count query posted on the issue, and the option to reopen with was named.
- **P2:** a closing comment said its aftercare was "parked on #598 with a 2026-12-07 trigger", but no Parked line was ever written. It was found at close-out and filed as a dated issue. **Candidate:** close-out greps the epic's closed children's last comments for "parked on #<epic>" and checks each one against the Parked section. From this run only.

**Pre-flight (F)**
- **F1:** four pre-flights were corrected in place: a dependency that nothing imported, a pytest ini filter that does reach `pytest_configure` under 9.2, an `npm audit` result, and release advice. Each was struck through visibly, and the implementer's own check of the brief caught most of them.
- **F2:** the release advice was "bump, but no restart needed". The host's OpenAPI parity guard flags a pulled version that was never restarted. **Candidate:** a pre-flight's release advice is checked against the host's deploy guards, not only the code path. From this run only.
- **F3:** after a 16-hour outage (egress-IP drift plus an unsupervised restart), the coordinator wrote that a pre-restart check "would have prevented" it. DB-backed routes were failing throughout anyway, so what the check saves is narrower. The claim was corrected in the next check-in. Check a counterfactual against the incident's own timeline before posting it.

**Harvest (H)**
- **H1:** run records hold unfiled follow-ups. The host-patching run's record listed a `uv.lock` advisory that no Dependabot alert showed. The coordinator traced who could reach it (only an email validator called with `check_deliverability=False`) and filed it, and it shipped the same evening. This is the existing "follow-ups the PR mentions but never filed" rule, applied to an ops record instead of a PR.
- **H2:** an implementer posting its own correction comment before building was routine by mid-run. Its "everything holds except…" comment became the place where line drift and premise errors landed.

**Writing the epic (W)**
- **W1:** the editor refused writes twice for its own lint (a multi-line note, a short cross-repo ref), and once for a note on a ref that only appeared second on a bundled line. Each refusal cost one retry and nothing else.

**Tags (T)**
- **T1:** implementers missed the release tag four times. The coordinator pushed it, on standing approval, until a timer (#631) checked the tag nightly. A missed step that recurs became a guard, not a reminder.

### Rules this run would add
1. `--account` flags a ticked line with an open ref (A1).
2. Close-out reconciles "parked on the epic" claims in closed children's comments with the Parked section (P2).
3. Release advice in a brief names the host guard it satisfies (F2).
4. A child that changes the verify surface updates the recipe in the same write (A2).

### Addendum: after the close (2026-11-14 to 11-15)

Filed as a comment on gregoryfoster/skills#642, with the operator's consent. The thread kept coordinating for about a day after the epic closed. It ran an FYI closure, a new cross-repo priority lane (in a private sibling repo: three issues, two releases) and a supervised data-apply, all without an epic. The operator noticed and asked for a hand-off. Candidate rules:

1. **A new priority after close opens a new epic, or a lane on one, not epic-less coordination.** The close-out section says a continuing thread restates its role. It doesn't say what to do when the operator sets a *new* priority. Here the state lived only in issue comments and host memory, until a hand-off comment on the closed epic gathered it. Rule: when a new priority arrives after close, propose creating an epic before the first pre-flight.
2. **A pre-flight that names a guard as the backstop reads that guard's coverage first.** The CannObserv/power-map#812 pre-flight said `schema-parity` would catch a skipped unique index. That audit reads constraints, functions and triggers, not indexes. The implementer caught it, the claim was corrected in place, and the follow-up is CannObserv/power-map#816.
3. **The brief's release section states the tag form and who closes the issue.** One release was tagged lightweight where its predecessors were annotated, because the implementer's host steps wrote `git tag`. The same thread closed its issue at deploy, before the coordinator verified it. The sibling release's implementer had left both for the check-in. Both would have been prevented by one line in the brief.
4. **Relay deploy facts to a sibling coordinator promptly.** The sibling epic's check-in ran a minute before the deploy, so it recorded "not yet tagged or deployed" for a dependency that was live. A relay was posted afterwards.
