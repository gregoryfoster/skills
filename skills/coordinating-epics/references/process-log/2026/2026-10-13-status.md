## Session 2026-10-13 — CannObserv/status#16

The second run, and the first with no design doc and no existing epic. The coordinator built the epic on 2026-10-01 from status's open issues and a one-line rule from the operator: *"prioritize bugs and smaller workstreams."* Status is the cohort's monitoring service. Much of the work arrived from other repos as onboarding requests, so the run carried operations as well as code. The epic closed on 2026-10-13 on an empty re-scan, and is still closed as of 2026-10-14. Findings 8–98 were posted on gregoryfoster/skills#348 after the check-ins. Finding 56 was an addendum to check-in 12.

### Shape

- **Way in:** a backlog plus a rule. The coordinator read every open issue in full, comments included, and tagged each by type, size and touch surface. It sorted them by the rule and wrote its own tie-breaks into the epic for the operator to challenge (8).
- **Children:** 7 in the original scope and 23 slotted mid-run, 30 in all:
  - 10 follow-ups filed by implementing threads;
  - 9 onboarding requests from consumer repos;
  - 2 port-backs, bugs found while porting status's code to a sibling;
  - 2 from operator approvals.

  One closed as not planned.
- **Check-ins:** 29, over 12 days (2026-10-01 to 2026-10-13).
- **Tracking:** a plain task list of `#N` links, without native sub-issues (22).

### What was different

- **No design doc set the order.** The order came from a rule the coordinator applied. Where the rule disagreed with itself, the coordinator stated its call once (9, 75).
- **It was an active repo.** The tail outgrew the original scope more than three to one, so the starting list was a poor guide to the end (48, 98).
- **The work was operations as well as code.** Onboarding requests recurred until each hand-off was only its difference from the last one (17, 57, 81).
- **Calendar windows set the order and the deploy times.** A sibling epic's 7-day production soak gated changes to the sweep (10, 30, 31).
- **A chain of review-born follow-ups formed.** Each item's code review filed the next one, four links long. The chain ended when the hand-off asked for a structural guard test (83, 86, 88, 90).

### Findings that changed the protocol

**Creation**
- Backlog plus a rule is its own way in. Read every issue and its comments, tag type, size and surface, sort by the rule, and write the tie-breaks into the epic (8).
- When the rule conflicts with itself ("bugs first" against "smaller first"), state the call once, at creation, on the order line (9). Write later conflict calls there too (75). An operator override is logged on the same line (52).
- Native sub-issues are optional for a small single-repo epic (22).
- The checklist needs an **ops** type next to bug, hardening and feature (17).

**Verify**
- Closed is not live, in either direction. One child closed at merge and deployed hours later; another stayed open until a host move was done. Verify on the live system: the served build, the schema state, the first pass after the deploy (34, 46).
- The deployed commit is not always the tip. A docs-only commit can follow the deploy, so check CI on both (15).
- The structured closing comment from `shipping-work-*`, plus CI, was enough evidence (14). Use its claims as the verification steps, and re-run them (33). Confirm "contract unchanged" from `git diff --stat` on the frozen fixtures, not from the comment (84).
- Verification is read-only. The coordinator tested a symlink protection by attempting the write on the production link. Had the protection failed, production would have pointed at `/tmp`. Read the permissions instead, or test on a scratch copy (45, 61).
- Judge deviations and rehearsals by what they proved, not by whether they followed the script (24, 71).
- A tests-only change is verified by its own reproduction method and its diff stat. A routine glance at each watcher's last verdict still caught an untracked rate-limit 403 (64, 66).
- A dependency bump inside a bug fix gets checked against the host's dependency rules (89).
- For a periodic job, look back at least one full period plus jitter, or ask the timer when it last ran. A window that started just after the last run made a healthy check look silent (95).
- Check each "known limit" for whether it needs a follow-up, and record the answer even when it is no (16).
- "Not planned" is a completed outcome. The line records the reasons and the reopen conditions (67).
- For an onboarding item, confirm its first scheduled run at the next check-in, from the access log (63, 97).

**Harvest**
- A closed issue's chosen option can change a remaining issue's trade-offs. Re-read the open items' options against what closed, and rewrite the overlap notes rather than appending to them (29, 32, 37).
- One issue's done state can become the next issue's design constraint. A docs commit after every deploy would have made the "live lags `main`" alert fire after every ship (25).
- Consumers read the closing comments as documentation and adopt new behaviour from them, which is one more reason to require the structured comment (79).

**Re-scan**
- The epic carries `Last check-in` and `Last issue seen` lines, so the thread can be lost without losing the cursor (18, 26).
- Slot a follow-up as soon as it is seen, even before the issue that spawned it closes (27). Re-run its evidence before sizing it, since its table is a snapshot (28).
- The re-scan sources go beyond new issues. They include sibling and parent epics listed as "not tracked here" (39), comments on closed children made after they closed (74), and issues in sibling repos that cite our closed children's code (49, 59).
- A ticked item that comes back as a bug stays ticked. Its fix is a new item that links back (50).
- Order an issue's follow-ups by how they depend on each other (38). A test flake goes after the bug that shares its file (51).
- A **Watching** section sits between ignoring something and filing it: the observation, the threshold and the evidence, re-checked at every re-scan (65).

**Blockers and gates**
- Time windows are blockers too, and are re-checked at every check-in (10, 30).
- A calendar gate constrains the deploy, not the start. Hand off early, with `deploy no earlier than <ts>` in the line and the prompt (31). Strike an expired gate with its date rather than deleting it (36).
- A release "available" when the issue was written can be superseded by hand-off. Re-check the other repo's tags and unreleased changelog (47).
- Check an ops request's preconditions from our side: the tailnet peer it needs (53), or a credential only another repo holds (76).

**Hand-off**
- Look at the live system the issue touches before writing the prompt. Doing so turned up duplicate check-runs on one SHA, a hand-created monitor the operator owned, an API that wasn't frozen, and a wider attack surface than the issue named (12, 41, 44).
- Put hazards in the prompt as things to weigh, not rules (11).
- A brief that repeats an issue's claim adds no checking. Write "the issue says X", or verify X with a query that could have shown it false (35). Verify a request's *reasoning* against the code too: a second key didn't deliver the isolation the request wanted (68).
- Quote a sibling's fix as a reference, with the property it relies on. Never dictate the line. The sibling's helper was an allowlist and status's a denylist, so the quoted line would have broken seven tests (62).
- The kickoff prompt carries the host memories that apply to the task (54).
- A decision only the operator can make is marked in the line and the prompt (55). Brackets such as `[Operator decision: …]`, with the coordinator's recommendation filled in, cost less than a round trip (70).
- Name feature interactions, and mark a predicted side effect as **expected** so it is confirmed rather than investigated (80, 82).
- For a recurring ops request, hand off only its difference from the last one, and propose a runbook section or script (57, 81). Drop a "to confirm" item once it no longer applies (58).
- For an input-class bug, ask for the whole class (83, 86). For a chain of review follow-ups about one kind of mistake, ask for a guard test that makes the whole kind fail CI (88, 90). Grep the pattern a review-filed follow-up names, since its scope is often narrower than the defect (87).
- For a flake, ask for a way to force the failure, not more loops (96).
- For a batch request with a long tail, decide the closing rule at hand-off: close with a named remainder (91, 92). Then ask what the waiting protects against, and whether the system already covers it (93).
- When a coordinator claim changes an operator plan, the prompt asks the implementer to confirm it against the code and tests first (94).
- Accept any durable record of the implementer's decisions, in the plan or on the issue (40, 42).

**State and writes**
- Read, then assert, then write, with `test -s` on the body file (20). Ticks are idempotent (`- \[[ x]\] #N`), and the write is chained with `&&`, never `;` (56).
- Implementers may tick. Only the coordinator annotates, and a pre-ticked box is a claim to verify (56, 60).
- Each ticked line becomes a log entry: the shipped range, the date it went live, and the option chosen (21).

**Operator**
- A waiting-on-external state is an option the operator can take, not a default the coordinator pushes (23).
- A product question raised by an onboarding request goes to the operator. The onboarding thread doesn't settle it (69).

**Close-out**
- Promise to close only after a re-scan comes back empty. Call the last item the "last *known* item" (48).
- Close-out needed four things: an empty re-scan, the Watching section resolved with its evidence, a summary grouped by theme rather than issue order, and the live state left behind. `gh issue close --comment` posted the summary and closed the epic in one call (98).

### Reversals

- **One writer.** The rule was "only the coordinator edits the epic" (19). Implementers ticked their own boxes anyway, twice, and the coordinator's edit crashed on the pre-ticked box (56). The replacement: implementers may tick, and the coordinator annotates and verifies (60). The later rule won. v1 has `epic-edit.sh --accept-ticks`.
- **Waiting on external.** At first a waiting state was proposed as the default for an ops task's external tail (17). It became an option the operator can take (23), and then "close with a named remainder" (91, 92). The named remainder won.
- **Decisions before code.** The prompt asked for decisions on the issue before implementing (40). An implementer used an approved plan commit instead, and the rule became "any durable record" (42). The later rule won.
- **Bugs first.** Applied strictly, bugs-first put a latent bug ahead of operator-approved onboarding requests with a repo waiting. The requests went first, with the reasoning on the order line (75). Order rules yield to a stated call.
- **The end.** The coordinator said the last planned item would close the epic. It closed with three follow-ups. The epic ends on an empty re-scan instead (48, 98). The later rule won.

### What v1's scripts would and wouldn't have caught

- **Would have caught the pre-ticked box.** `epic-edit.sh` sees a foreign tick and refuses with exit 3 until `--accept-ticks #N` names it. Its `tick` op holds when the box is already ticked, and a refusal writes nothing, so the `;`-chained re-post can't happen (56, 60).
- **Would have found the late arrivals.** `scan.sh` lists follow-ups filed mid-flight by watermark (27). With `updated_at` since, it would have found the operator decision posted on a closed child after it closed (74). The `Last check-in` and `Last issue seen` lines are what it reads (18, 26).
- **Partly on sibling epics.** The updated-since cursor shows a same-repo sibling epic as updated (39), but not what changed in it. Issues in sibling repos that cite our code (49) are outside both scripts. Only refs already written into the body are read.
- **Wouldn't have caught closed-but-not-live** (34, 46), CI on two SHAs (15), or a journal window that started too late (95). Verification isn't scripted in v1, and `verify-ci.sh` is v1.1.
- **Wouldn't have stopped a write to production** during verification (45). That is a rule for the coordinator, and no script runs it.
