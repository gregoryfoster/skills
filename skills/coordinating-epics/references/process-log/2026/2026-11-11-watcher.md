### Findings (368-F4 onward)
4. **Adopting an existing cross-repo parent.** A dry run on a copy of the body, against the tests' fake `gh`, found three problems before any write:
   - a date-only `Last check-in`;
   - six repos' watermarks on one header line, which a `header` op would rewrite whole;
   - one ref leading two bullets, so `note` refused it as ambiguous.

   Filed then (gregoryfoster/skills#408, and a comment on gregoryfoster/skills#399). Dry-running against a copy first is worth keeping.
5. **The transfer found an unrecorded go.** The operator's go for F1 had been relayed into the parent by Archiver's coordinator as a comment, and never written into the body. The hand-off comment, which carried only what the body didn't hold, surfaced it, and the hand-off's own write recorded it. Candidate rule above.
6. **Lines kept in both epics drift.** Watcher's children had a line in the parent's Issues list and in #394's *Headless cutover* section. #394's line carried the evidence; the parent's carried a tick and a one-line pointer.
   - One child closed 11-03 and was ticked on #394 the same day. The parent's tick waited until 11-10, when the last child closed and the coordinator re-read the parent's open lines.
   - No script compares two epics, so nothing flagged it.
   - Replicator's H1 and notifier's H1 reached the rule from the other side (one epic only; the other points). This run is the counter-example.
7. **A fold shares a thread, not an exit.** At the fold, #394's exit criterion took on the parent's ("then #368 closes with this epic"). At the end, the operator decoupled them (2026-11-10): the parent closes when its own exit is met, which is its sibling epics closing. #394 still has unrelated Tier 3 work, so the coupling would have held the parent open for no reason. Decoupled, it closed the next day, minutes after its last sibling epic.
8. **The deletion briefs missed things every time, and the pre-build review caught every miss.** Each brief ran a grep-and-trace pre-flight on `origin/main`. Even so:
   - **Dashboard:** 8 items missed.
   - **API:** 8 small corrections. A "last reader" claim was wrong; it was corrected in place in two comments.
   - **Schema drops:** 3 wrong claims, including that CI's `migrations` job exercises the downgrade (it doesn't), and a production query that missed the hazard that mattered (archived rows still active).
   - **Docs:** 3 `src/` comments and several stale claims.
   - **Test flake:** a "candidate member" of the bug class that wasn't one.

   In every case the implementer's "review the brief against the code and post corrections before you build" caught it before code. Each was logged as a coordinator error and corrected in place. This confirms an existing rule; it adds no new one.
9. **A precedent's precondition, again.** The repo's column-drop precedent restarted before migrating, which works only for nullable columns. One drop had a NOT NULL column with no default, so the brief named stop → migrate → start instead. This is the existing hand-off rule ("name the precondition that made it safe there") working as written.
10. **A gate on a natural event never fired.** F3's last check was "Archiver's first live send after T". No content change happened in the 4 days after T, so there was nothing to send. The operator dropped the gate and took the shadow parity as the proof. Written with a time-box and a named fallback, the gate would have closed on schedule. Candidate rule above.
11. **Two-sided read-backs keyed on one id.** F4's read-back had a Watcher half and an Archiver half, posted by different coordinators. Both quoted the same command id, which matched the bus message id, so joining them took one comparison. From this run only.
12. **The idle wake** (#394's finding 1, operator 2026-10-27) came from this shared thread. Its entry belongs to #394's run; it's noted here only because it caught two sibling moves for this parent.

### What the scripts caught or missed
- **`scan.sh` reads one repo.** The five sibling repos were re-scanned by hand, as v1 said (gregoryfoster/skills#400). It also runs with one token, so the host's private sibling repos, reachable only with per-repo tokens, show as "unreadable" in every report. That's 14 warnings per scan, read past each time. A per-repo token map would end that.
- **`epic-edit.sh`** took every write on the parent with fully qualified refs, and its foreign-edit check never fired across the two threads. It has no cross-epic check, so finding 6 went unseen.
- **`--scan`'s header guard** refused nothing it shouldn't have. "Last issue seen already reads so" is benign, and it showed up on most check-ins once the watermark stopped moving.
